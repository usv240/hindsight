# Detection benchmark and real-project validation - 2026-07-28

Two things that a hand-picked demo cannot tell you: how the detector behaves
across the defect's full range, and whether it survives contact with SQL nobody
wrote for it.

## 1. Detection benchmark

`hindsight benchmark` sweeps the defect from total reach to almost none, three
seeds each, with a matched clean control for every case. Full output:
[`evaluations/benchmark.json`](../../evaluations/benchmark.json).

**42 cases - 21 leaked, 21 clean.**

| | |
|---|---:|
| precision | **1.000** |
| recall | **1.000** |
| F1 | **1.000** |
| false positives | **0** |
| false negatives | **0** |
| total runtime | 3.7s |

### The result that matters

Recall as the defect becomes subtler, split by which route fired:

| Reach | Mean AUC delta | Statistical route | Overall |
|---:|---:|---:|---:|
| 100% | 0.1768 | 100% | 100% |
| 70% | 0.1578 | 100% | 100% |
| 40% | 0.1086 | **0%** | 100% |
| 25% | 0.0752 | **0%** | 100% |
| 15% | 0.0451 | **0%** | 100% |
| 8% | 0.0262 | **0%** | 100% |
| 2% | **0.0066** | **0%** | 100% |

The statistical route stops firing entirely below 40% reach. At 2% reach the
performance difference is **0.0066 of AUC** - invisible to any threshold anyone
would set. The deterministic SQL/time proof catches all of them.

This is the argument for two independent confirmation routes, measured rather
than asserted. A leakage detector built only on statistics would miss five of
these seven bands.

### How to read the headline

**The perfect precision and recall are partly true by construction, and should
not be read as field accuracy.** Ground truth here is structural: a case is
"leaked" if its query joins a post-outcome source with no availability guard, and
the deterministic route reads that same query.

What the benchmark *does* measure honestly:

- **The statistical route's recall curve.** It is never told about the SQL, so its
  collapse below 40% reach is a real measurement.
- **Zero false positives** across 21 guarded queries. It could have flagged them.
- **The AUC delta shrinking toward invisibility**, which is precisely why a
  statistics-only detector is insufficient.
- Runtime per case.

What it cannot tell you: performance on real-world SQL where a guard is expressed
in ways the parser does not recognise. That needs a corpus of real transformations.

## 2. Real-project validation

Run against **[dbt-labs/jaffle-shop](https://github.com/dbt-labs/jaffle-shop)**, a
public dbt project written by someone else, with no knowledge of this tool.

```text
$ hindsight scan-sql jaffle-shop/models --post-outcome-table stg_order_items

Scanned 13 SQL file(s)

VIOLATIONS (1) - post-outcome data with no cutoff:
  marts/order_items.sql
    reads stg_order_items without an availability guard

clean: 0   violations: 1   unchecked: 0   no post-outcome source: 12
exit 3
```

**This is not a finding against jaffle-shop.** `stg_order_items` is not actually a
post-outcome table; it was nominated as one to exercise the scanner. jaffle-shop
has no leakage problem. What the run demonstrates is that the tool reads a real
dbt project correctly and reports precisely which model touches a nominated source
without a guard.

### It found two real bugs in Hindsight

Worth recording, because the first is exactly the failure this project exists to
prevent:

1. **dbt models were silently reported as clean.** Every model is a Jinja template
   (`{{ ref('stg_orders') }}`), which the SQL parser could not read, so all 13
   returned zero tables and were filed as *"no post-outcome source"*. A false
   negative wearing a pass. `scan-sql` now resolves `ref()` and `source()`, strips
   statement-level macros such as `config()`, and substitutes remaining Jinja.

2. **An unparseable query fell through to clean.** An `indeterminate` parse result
   was treated as "not applicable". It is now reported as **unchecked**, and
   unchecked files force exit code 2. A file that was never examined has not
   passed.

Both are covered by regression tests in `tests/test_scan.py`.

## Reproducing

```powershell
uv run hindsight benchmark
git clone --depth 1 https://github.com/dbt-labs/jaffle-shop
uv run hindsight scan-sql jaffle-shop/models --post-outcome-table stg_order_items
```
