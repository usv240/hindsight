# DataHub surface coverage - verified 2026-07-29

This records which rule-named DataHub surfaces Hindsight uses and what was
proved against a live DataHub Core instance rather than asserted.

| Surface | Used | How |
|---|---:|---|
| Context graph | yes | Column-level lineage, ML entities, schema, profiles |
| MCP Server | yes | Discovery, lineage reads, governed mutations |
| **Agent Context Kit** | **yes** | `get_lineage_paths_between` as the core path primitive |
| DataHub Skills | yes | Locally validated `datahub-ml-release-audit` Skill |
| **DataHub Actions** | **yes** | Isolated event-driven release gate on model metadata changes |
| Analytics Agent | no | Not applicable; this is not a text-to-SQL product |

## Agent Context Kit

Hindsight uses `get_lineage_paths_between` because it returns a column-level,
directional catalog path. The live query resolved this chain:

```text
payment_recorded_at
  -> urn:li:query:d47c395f75a3ca4422cf5f44739b620e001eeb455358b323ff42161e4acc9377
  -> days_since_last_payment
resolved_by: agent_context_kit
```

The middle hop is DataHub's query entity: the catalog identifies the
transformation connecting the columns. The wrapper also distinguishes "the
catalog says no path" (`available: true`, `found: false`) from "the catalog
could not be reached" (`available: false`). A negative is evidence; an outage is
not.

## DataHub Action: live end-to-end proof

The Action is built on the official
`acryldata/datahub-actions:v1.5.0.6-slim` image. Its Docker build installed
Hindsight and finished with `No broken requirements found`; the running process
reported `DataHub Actions version: 1.5.0.6+docker`.

The proven chain was:

1. Start the isolated Action on DataHub's Docker network with a unique Kafka
   consumer group and one exact-bound model URN.
2. Upsert that real `MLModel` through DataHub Core.
3. DataHub publishes the change on `MetadataChangeLog_Versioned_v1`.
4. The Action consumes the exact model's `mlModelProperties` `MetadataChangeLogEvent_v1`.
5. Hindsight runs the audit and writes an append-only JSONL result inside the
   isolated container.

Exact target:

```text
urn:li:mlModel:(urn:li:dataPlatform:mlflow,hindsight.credit_default_v1_leaky,PROD)
```

Exact Action result:

```json
{"audit":"credit_default","confirmation_route":"point_in_time_collapse","evidence_model_urn":"urn:li:mlModel:(urn:li:dataPlatform:mlflow,hindsight.credit_default_v1_leaky,PROD)","exit_code":3,"incident_raised":false,"release_decision":"block","urn":"urn:li:mlModel:(urn:li:dataPlatform:mlflow,hindsight.credit_default_v1_leaky,PROD)","verdict":"confirmed"}
```

The normalized result is preserved in
[`hindsight-action-proof.json`](hindsight-action-proof.json). Kafka consumer
offsets were at zero lag after the proof. This replaces the earlier
Windows/Python-3.12 limitation: the deployed Action now runs in the official,
compatible Linux runtime rather than sharing the main app's environment.

Deployment and reproduction commands are in
[`docker/ACTION.md`](../../docker/ACTION.md).

### Deliberate constraints

1. **Exact binding.** The Action rejects every entity type and URN except the
   configured target. A model audit cannot be attached to whichever event
   happens to arrive next.
2. **One result per event.** Exact Kafka redeliveries are deduplicated after a
   successful audit. Failed audits remain retryable.
3. **Observe-only automation.** The proof configuration raises no incident and
   never publishes governed metadata. Human approval remains mandatory for the
   separate write-back workflow.
4. **Failure isolation.** Audit failures are logged without stopping the shared
   event pipeline.
5. **Durable local evidence.** When `proof_log_path` is configured, each result
   is appended as JSONL for machine verification; it is not a catalog mutation.

## Offline guarantee

The Kit, DataHub SDK, and Actions runtime remain optional. With none installed
and no DataHub reachable, `hindsight demo` still runs, and integrations degrade
to explicit `available: false` results rather than exceptions. Fifteen tests in
`tests/test_integrations.py` cover the integration contract.
