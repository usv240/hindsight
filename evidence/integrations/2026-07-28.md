# DataHub surface coverage - 2026-07-28

The rules name five DataHub surfaces. This records which are used, how, and what
was proven against a live instance rather than asserted.

| Surface | Used | How |
|---|---|---|
| Context graph | yes | Column-level lineage, ML entities, schema, profiles |
| MCP Server | yes | Discovery, lineage reads, governed mutations |
| **Agent Context Kit** | **yes** | `get_lineage_paths_between` as the core path primitive |
| DataHub Skills | yes | `datahub-ml-release-audit`, PR prepared upstream |
| **DataHub Actions** | **yes** | Event-driven release gate on model creation |
| Analytics Agent | no | Not applicable - this is not a text-to-SQL product |

## Agent Context Kit

Adopted for one specific reason, not to tick a box. The Kit ships the exact
primitive this project is built on:

```python
get_lineage_paths_between(source_urn, target_urn,
                          source_column=..., target_column=..., direction=...)
```

That is a **column-level, directional** path query. Previously the path was
reconstructed by hand from a general lineage walk; now it is queried from the
catalog, which matters when the entire claim is "here is what the graph says".

Verified live:

```text
$ hindsight trace-lineage \
    --source-urn '...hindsight.phase0.payment_events_1785182428,PROD)' \
    --source-column payment_recorded_at \
    --target-urn '...hindsight.phase0.leaky_features_1785182428,PROD)' \
    --target-column days_since_last_payment

{ "available": true, "found": true, "hops": 2,
  "path": ["payment_recorded_at",
           "urn:li:query:d47c395f75a3ca4422cf5f44739b620e001eeb455358b323ff42161e4acc9377",
           "days_since_last_payment"],
  "resolved_by": "agent_context_kit" }
exit 3
```

The middle hop is a **query entity**: DataHub reports not just that the columns
are connected, but which transformation connects them. The evidence chain can
therefore cite the catalog's own record of the SQL rather than a file on disk.

### A distinction the wrapper had to learn

The Kit raises `ItemNotFoundError: No lineage path found` when there is no path.
The first implementation treated every exception as "could not reach DataHub",
which would have let a real negative masquerade as an unknown. `available` and
`found` are now separate fields: **"the catalog says no path" is evidence against
leakage**; "we could not ask" is not evidence at all.

## DataHub Actions

Hindsight as an agent that watches, rather than a tool someone remembers to run.

`docker/hindsight-action.yml` subscribes to `EntityChangeEvent_v1`, filtered to
`LIFECYCLE / CREATE / mlModel` so irrelevant events are discarded before
deserialization. On a matching event the gate audits the model and records the
verdict.

```powershell
datahub actions -c docker/hindsight-action.yml
```

### Proven end to end, not just unit tested

Everything else in this project is demonstrated rather than asserted, so the
action should be too. The full chain was exercised against the live stack:

1. A real `MLModel` was emitted to DataHub Core.
2. DataHub published the change to Kafka on `MetadataChangeLog_Versioned_v1`.
3. The event was consumed off the bus and matched to the emitted model.
4. The gate audited it and returned `block`.

```text
emitted urn:li:mlModel:(urn:li:dataPlatform:mlflow,hindsight_action_probe_f1c82d,PROD)
observed our own model on the bus after 1 messages
INFO Hindsight: auditing newly created urn:li:mlModel:(...hindsight_action_probe_f1c82d,PROD)
INFO Hindsight: ... -> block (confirmed)
INFO Hindsight release gate stopping: 1 audited, 1 blocked
```

The action was also driven with a genuine `EntityChangeEvent` envelope (not a
dict stand-in) to confirm it parses the real event shape, and it subclasses the
framework's `Action` base class once `acryl-datahub-actions` is installed.

**What was not proven:** DataHub's own `datahub actions run` process exits
immediately and silently on this machine. The CLI warns that Python above 3.11 is
not actively tested, and this environment is 3.12. That is a limitation of the
runtime on Windows/3.12, not of the action, and it is recorded here rather than
glossed over. Everything the action itself is responsible for is demonstrated
above.

### Two deliberate constraints

1. **It never publishes.** The action may raise an incident to notify; only a
   human may approve the evidence write-back. An autonomous process silently
   mutating governed metadata is precisely what this project argues against.
   A test asserts `publish_audit` does not appear anywhere in the action's source.

2. **It never takes the pipeline down.** An Action that raises stops every other
   consumer of the event stream, so audit failures are logged and swallowed.
   Covered by a test that points it at a nonexistent project root and asserts
   the pipeline survives.

## Offline guarantee

Both the Kit and the Actions framework are optional extras. With neither
installed and no DataHub reachable, `hindsight demo` still runs, and every
integration reports `available: false` with a stated reason rather than raising.
Fourteen tests in `tests/test_integrations.py` cover the degradation paths.
